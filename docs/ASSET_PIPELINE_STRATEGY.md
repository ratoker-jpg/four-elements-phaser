# ASSET_PIPELINE_STRATEGY.md

Status: accepted design (ARCH-02A)
Audience: GPT / task planning / GLM executor
Project: Four Elements Phaser

---

## 1. Purpose

Define a systemic, repeatable pipeline for staging, validating, generating, and integrating art assets into the Four Elements Phaser runtime. The pipeline must ensure that every new sprite, sheet, tile, icon, or effect can be added through a single well-defined workflow — not by ad-hoc file copying and manual key registration.

The pipeline does not replace the existing building placement metadata system (ARCH-03 / BUILD-ANCHOR). It wraps around it, providing the broader asset lifecycle that the building metadata generator is one part of.

---

## 2. Current state summary

### 2.1 Asset manifest

`src/assets/assetManifest.ts` defines a small base subset of assets:

- 3 terrain tiles (sand, dark, light)
- 1 HQ (cyan)
- 1 harvester spritesheet (cyan)
- 3 mineral sprites (small, medium, large)

This file defines `ASSET_KEYS`, `ASSET_PATHS`, and `SPRITESHEET_8X8_256`. It is the original manifest from PR1, but it now covers only a fraction of the assets actually loaded at runtime.

### 2.2 Building assets

`src/assets/buildingAssets.ts` loads 6 building types × 4 factions = 24 building PNGs, plus 3 non-cyan HQ PNGs. It has its own key convention (`building_{faction}_{suffix}`), path helpers (`getBuildingAssetKey`, `getBuildingAssetPath`), and a loader function (`loadBuildingAssets`). It bypasses `assetManifest.ts` entirely.

### 2.3 Civil unit assets

`src/assets/civilUnitAssets.ts` loads 4 builder sheets + 3 non-cyan harvester sheets = 7 spritesheets. It uses `SPRITESHEET_8X8_256` from `assetManifest.ts` for frame config, but has its own key convention and loader function.

### 2.4 Modular unit assets

`src/assets/modularUnitAssets.ts` loads 4 factions × 8 directions × 2 parts (Wasp hull + Smoky turret) = 64 individual PNGs. Each is a single-frame direction image, not a spritesheet. Key format: `wasp_m0_hull_{faction}_dir{N}`, `smoky_m0_turret_{faction}_dir{N}`.

### 2.5 Building placement metadata

`src/assets/buildingPlacementMeta.ts` defines the `BuildingPlacementMeta` interface and a runtime lookup registry. `src/assets/generatedBuildingMeta.ts` contains 24 entries (6 types × 4 factions), auto-generated by `tools/generate_building_meta.py`. The Python script scans PNG files, computes alpha bounds and ground-line ratios, and outputs committed TypeScript. The Node.js wrapper `tools/generate_building_meta.mjs` handles cross-platform Python invocation.

### 2.6 PreloadScene

`src/phaser/PreloadScene.ts` manually calls four separate loaders in sequence: inline terrain/HQ/harvester/resource loading from `ASSET_KEYS`/`ASSET_PATHS`, then `loadModularUnitAssets(this)`, then `loadCivilUnitAssets(this)`, then `loadBuildingAssets(this)`. There is no manifest-driven or data-driven loading; the load sequence is hardcoded.

### 2.7 Public asset tree

```
public/assets/
  tiles/              3 sand PNGs
  environment/        3 mineral PNGs
  factions/
    {cyan,green,yellow,purple}/
      buildings/      HQ + 6 building PNGs per faction = 28 total
      units/          builder_8x8_256.png + harvester_8x8_256.png per faction = 8 total
  units/
    chassis/wasp_m0/{faction}/  8 direction PNGs per faction = 32 total
    weapons/smoky_m0/{faction}/ 8 direction PNGs per faction = 32 total
```

Total on disk: ~106 PNG files. No source sheets, no staged assets, no generated variants.

### 2.8 Asset policy

`docs/ASSET_POLICY.md` requires explicit approval for asset copying, forbids blind folder copying, and mandates that assets be documented in the manifest. However, the current codebase has drifted from this: `buildingAssets.ts`, `civilUnitAssets.ts`, and `modularUnitAssets.ts` all load assets that are not listed in `assetManifest.ts`.

## 3. Problems / gaps

### 3.1 Fragmented asset registration

Four separate files define asset keys and loading logic. There is no single source of truth for "what assets exist." Adding a new asset type requires touching multiple files and hoping the key conventions stay consistent.

### 3.2 Manifest drift

`assetManifest.ts` lists 9 entries. The actual runtime loads ~106 assets. The manifest is not the source of truth for the majority of assets. Any validation based on the manifest would miss most of the loaded assets.

### 3.3 No naming enforcement

Key conventions differ across files:
- `assetManifest.ts`: `terrain_sand`, `hq_cyan`, `harvester_cyan`, `mineral_small`
- `buildingAssets.ts`: `building_{faction}_{suffix}` (underscore suffixes)
- `civilUnitAssets.ts`: `{unitType}_{faction}` (e.g. `builder_cyan`)
- `modularUnitAssets.ts`: `wasp_m0_hull_{faction}_dir{N}`

There is no single naming rule or validator. A typo in a key produces a silent load failure at runtime.

### 3.4 No source/staged/generated separation

All assets are in `public/assets/`, which serves double duty as both the authoring location and the runtime location. There is no source sheet folder, no staging area for review, no generated output folder, and no way to re-derive runtime assets from source.

### 3.5 No asset validation tooling

There is no script that checks:
- whether all referenced assets exist on disk
- whether all assets on disk are referenced by the manifest
- whether key names follow naming rules
- whether spritesheet dimensions match declared frame config
- whether PNGs have unexpected content (red backgrounds, checkerboard artifacts)
- whether assets are visually grounded/aligned

The building metadata generator (`generate_building_meta.py`) is the only validation tool, and it covers only one asset family (buildings).

### 3.6 No preview or audit capability

There is no way to view all loaded assets in a structured way, compare source vs. runtime appearance, or detect visual regressions. The building metadata generator prints a console table, but there is no visual output.

### 3.7 Duplicate-key avoidance by convention

`buildingAssets.ts` skips cyan HQ because `assetManifest.ts` already loads it. `civilUnitAssets.ts` skips cyan harvester for the same reason. This convention is fragile: if someone removes the entry from `assetManifest.ts`, the asset silently disappears; if they forget to skip it, the duplicate key causes a runtime error.

### 3.8 No sheet processing

The project has no tooling to process source sprite sheets into runtime-ready frames, tiles, or individual PNGs. The existing `8x8_256` spritesheets are committed as-is, presumably authored directly at runtime size. There is no pipeline for cutting sheets, resizing, or generating variant sheets.

### 3.9 No missing-source report

When a building PNG is missing, the Python generator prints a console warning and skips it, but there is no persistent report or CI check. Missing assets are discovered only at runtime as Phaser load errors.

## 4. Target pipeline model

```
Source Sheets          Staged Assets          Generated Assets          Runtime
─────────────          ──────────────          ─────────────────         ───────
art/source/      →     art/staged/       →     art/generated/      →    public/assets/
  buildings/            buildings/              buildings/               factions/*/buildings/
  units/                units/                  units/                   factions/*/units/
  modular/              modular/                modular/                 units/chassis/ + weapons/
  terrain/              terrain/                terrain/                 tiles/
  resources/            resources/              resources/               environment/
  fx/                   fx/                     fx/                      (loaded by config)
  ui/                   ui/                     ui/                      (loaded by config)
  decor/                decor/                  decor/                   (loaded by config)
```

Flow:

1. **Author** creates or edits source sheets in `art/source/`.
2. **Stage** — the author or a script copies approved assets to `art/staged/` with correct naming.
3. **Generate** — the processor reads `art/staged/`, validates naming and dimensions, generates runtime PNGs into `art/generated/`, and produces a manifest JSON and TypeScript.
4. **Integrate** — validated generated assets are copied to `public/assets/` and the TypeScript manifest is imported by PreloadScene.
5. **Verify** — a sample viewer shows all generated assets. An audit report lists missing sources, naming violations, dimension mismatches, and crop warnings.

Steps 2-5 are partially automatable. Step 1 (authoring) is always manual. Step 4 (integration into PreloadScene) is deferred to a later ARCH-02 phase because it requires runtime code changes.

## 6. Asset naming rules

### 6.1 General rules

- All keys use `lowercase_snake_case`.
- All filenames use `lowercase_snake_case.png`.
- Hyphenated building types in state (`raw-storage`, `power-plant`) map to underscore key suffixes (`raw_storage`, `power_plant`).
- Faction names are always lowercase: `cyan`, `green`, `yellow`, `purple`.
- Direction indices are zero-padded where applicable: `dir0`..`dir7` for 8-direction sprites.

### 6.2 Per-family key patterns

| Family | Key pattern | Example |
|--------|------------|---------|
| Terrain | `terrain_{variant}` | `terrain_sand`, `terrain_sand_dark` |
| Buildings | `building_{faction}_{type_suffix}` | `building_cyan_separator`, `building_green_power_plant` |
| HQ | `hq_{faction}` | `hq_cyan`, `hq_green` |
| Civil units (sheet) | `{unit_type}_{faction}` | `builder_cyan`, `harvester_green` |
| Modular hull | `{chassis}_{mark}_hull_{faction}_dir{N}` | `wasp_m0_hull_cyan_dir0` |
| Modular turret | `{weapon}_{mark}_turret_{faction}_dir{N}` | `smoky_m0_turret_green_dir3` |
| Resources | `{resource_type}_{size}` | `mineral_small`, `mineral_large` |
| Decor/obstacles | `decor_{name}` | `decor_rock_small` |
| FX | `fx_{name}` | `fx_dust_particle` |
| UI icons | `ui_icon_{name}` | `ui_icon_build_separator` |

### 6.3 Filename rules

| Family | Filename pattern | Example |
|--------|-----------------|---------|
| Terrain | `{variant}.png` | `sand_tile.png` |
| Buildings | `{type_suffix}.png` | `separator.png`, `raw_storage.png` |
| HQ | `hq_t1.png` | `hq_t1.png` |
| Civil units (sheet) | `{unit_type}_8x8_256.png` | `builder_8x8_256.png` |
| Modular hull | `{chassis}_{mark}_hull_idle_dir{N}_0.png` | `wasp_m0_hull_idle_dir0_0.png` |
| Modular turret | `{weapon}_{mark}_turret_idle_dir{N}_0.png` | `smoky_m0_turret_idle_dir0_0.png` |
| Resources | `{resource_type}_{size}_{variant}.png` | `mineral_small_02.png` |
| Decor/obstacles | `{name}.png` | `rock_small.png` |
| FX | `{name}.png` | `dust_particle.png` |
| UI icons | `icon_{name}.png` | `icon_build_separator.png` |

### 6.4 Validation

The `validate_manifest.mjs` script must verify:
- All keys match their family pattern.
- All filenames match their family pattern.
- No duplicate keys exist across all manifest sources.
- No orphan files exist on disk that are not referenced by any key.
- No keys reference files that do not exist on disk.

## 7. Sheet layout rules

### 7.1 Spritesheets

Civil units use 8×8 layout: 8 direction rows × 8 animation frames, total 64 frames per sheet.

Direction row order (DIR_ROW):
```
E=0, SE=1, S=2, SW=3, W=4, NW=5, N=6, NE=7
```

Idle frame is column 0 in every direction row.

Frame dimensions: `{frameWidth}×{frameHeight}` must be declared in the manifest. The current standard is 256×256.

Sheet pixel dimensions: `frameWidth * columns × frameHeight * rows`. For 8×8 at 256px: 2048×2048.

### 7.2 Building images

Buildings are single-frame PNGs, not spritesheets. They may have large transparent padding. The alpha-bounds generator strips this metadata but does not crop the PNG.

### 7.3 Modular unit images

Modular units (Wasp hull, Smoky turret) are stored as individual per-direction PNGs, not as spritesheets. This is 8 files per unit-part per faction. A future optimization may pack these into a spritesheet, but the current format is individual direction PNGs.

### 7.4 Terrain tiles

Terrain tiles are single-frame PNGs sized to fit the isometric tile (76×38 logical). Source tiles may be larger; the processor should validate that tile dimensions are consistent.

### 7.5 FX / particles

FX sprites are small individual PNGs or short spritesheets. Layout rules for FX will be defined when ARCH-13 (VFX) is implemented. For now, FX assets should follow `fx_{name}` naming.

### 7.6 UI icons

UI icons are single-frame PNGs. Size should be consistent within a set (e.g. all build menu icons at 48×48). The processor should warn if icon dimensions within a set differ by more than 2×.

## 8. Manifest / enabled keys model

### 8.1 Current model

The current model is fragmented:
- `assetManifest.ts` has `ASSET_KEYS` (9 entries) and `ASSET_PATHS`.
- `buildingAssets.ts` generates keys programmatically from `BUILDING_ASSET_FACTIONS × BUILDING_ASSET_TYPES`.
- `civilUnitAssets.ts` generates keys from `CIVIL_FACTIONS × CIVIL_UNIT_TYPES`.
- `modularUnitAssets.ts` generates keys from `MODULAR_FACTIONS × MODULAR_DIRECTIONS`.

### 8.2 Target model

A single `manifest.generated.json` file in `art/generated/` should contain:

```json
{
  "version": 1,
  "generatedAt": "2026-05-26T12:00:00Z",
  "families": {
    "terrain": {
      "keys": ["terrain_sand", "terrain_sand_dark", "terrain_sand_light"],
      "loadType": "image"
    },
    "buildings": {
      "keys": ["building_cyan_separator", ...],
      "loadType": "image"
    },
    "civilUnits": {
      "keys": ["builder_cyan", "harvester_cyan", ...],
      "loadType": "spritesheet",
      "frameConfig": { "frameWidth": 256, "frameHeight": 256, "endFrame": 63 }
    },
    "modularUnits": {
      "keys": ["wasp_m0_hull_cyan_dir0", ...],
      "loadType": "image"
    },
    "resources": {
      "keys": ["mineral_small", "mineral_medium", "mineral_large"],
      "loadType": "image"
    }
  },
  "paths": {
    "terrain_sand": "assets/tiles/sand_tile.png",
    "building_cyan_separator": "assets/factions/cyan/buildings/separator.png",
    ...
  }
}
```

Each family has an `enabled` flag (defaulting to `true`). Families that are not yet integrated into the runtime can be marked `enabled: false` so they are loaded for preview but not during gameplay.

### 8.3 Runtime manifest

`src/assets/generatedAssetManifest.ts` is auto-generated by the processor from `manifest.generated.json`. It is a committed TypeScript file that exports:

- `GENERATED_ASSET_MANIFEST` — a `const ... as const` object with all families, keys, paths, loadTypes, and enabled flags.
- `GeneratedAssetKey` — type union of all manifest path keys.
- `GeneratedAssetFamilyName` — type union of all family names.

`src/assets/runtimeGeneratedAssets.ts` provides scene-level loader helpers:

- `loadGeneratedImageAssetFamilies(scene, families)` — loads all image-type assets from the specified enabled families.
- `loadGeneratedBuildingAndHqAssets(scene)` — convenience wrapper for hq + buildings.

ARCH-02F implements this for hq + buildings families only. ARCH-02G adds civilUnits spritesheet loading. ARCH-02H adds modularUnits image loading. ARCH-02I adds terrain + resources image loading. All six families (hq, buildings, civilUnits, modularUnits, terrain, resources) are now loaded from the generated manifest. The old `loadBuildingAssets()` in `buildingAssets.ts` is kept as deprecated legacy fallback but is no longer called by PreloadScene. The old `loadCivilUnitAssets()` in `civilUnitAssets.ts` and `loadModularUnitAssets()` in `modularUnitAssets.ts` are similarly kept as deprecated legacy fallback. Terrain and resource keys in `assetManifest.ts` are marked `@deprecated`.

### 8.4 Key-to-path mapping

The manifest must contain an explicit `paths` map. Currently, paths are derived by convention (e.g. `assets/factions/${faction}/buildings/${filename}`). The manifest should make this mapping explicit rather than algorithmic, because:
- Not all assets follow the same directory pattern (modular units are under `units/` not `factions/`).
- Explicit paths are easier to validate (check file existence).
- Algorithmic derivation can be used as a fallback during generation, but the manifest is the source of truth.

## 9. Processor/generator responsibilities

### 9.1 Existing generator

`tools/generate_building_meta.py` currently:
- Scans `public/assets/factions/*/buildings/` for building PNGs.
- Computes alpha bounds, ground-line ratio, origin, scale.
- Outputs `src/assets/generatedBuildingMeta.ts`.
- Prints a console report with summary table and warnings.

This generator is building-specific and handles only the placement metadata concern. It does not generate the asset manifest, validate naming, or handle other asset families.

### 9.2 Target processor

A new `tools/process_art_assets.mjs` should:

1. **Scan `art/staged/`** for all asset files organized by family.
2. **Validate naming** against the per-family naming rules (section 6).
3. **Validate dimensions** against expected sizes (spritesheet 2048×2048, tile 76×38, etc.).
4. **Copy validated assets** to `art/generated/` with canonical filenames.
5. **Generate `manifest.generated.json`** with all keys, paths, families, load types, and enabled flags.
6. **Run the building metadata generator** (`generate_building_meta.py`) as a sub-step for the buildings family, incorporating its output into the manifest.
7. **Generate `audit-report.json`** with warnings for missing sources, naming violations, dimension mismatches, orphan files, and duplicate keys.
8. **Optionally copy** generated assets to `public/assets/` (controlled by a flag, not automatic).

### 9.3 Processing order

The processor should handle families in dependency order:
1. Terrain (no dependencies)
2. Resources (no dependencies)
3. Decor/obstacles (no dependencies)
4. Buildings (depends on terrain for footprint sizing)
5. Civil units (no dependencies)
6. Modular units (no dependencies)
7. FX (no dependencies)
8. UI icons (no dependencies)

### 9.4 Incremental processing

For MVP (ARCH-02D), the processor should handle one asset family (likely buildings or resources). It must be designed so additional families can be added incrementally without restructuring.

### 9.5 Relationship to existing building metadata generator

The existing `generate_building_meta.py` is a specialized processor for one concern (placement metadata) within one family (buildings). In the target architecture, it becomes a sub-step of the unified processor. The unified processor delegates building placement metadata generation to the Python script and incorporates its output into the manifest.

The Python script should not be rewritten in Node.js unless a clear benefit is demonstrated. PIL/Pillow is well-suited for alpha-bounds computation, and the script is a dev-only tool that does not affect the runtime bundle.

## 10. Preview/sample viewer responsibilities

### 10.1 Purpose

A standalone HTML page (`task/art-sample/index.html`) that shows all assets in `art/generated/` in a structured, browsable layout. This allows visual verification without running the full game.

### 10.2 Layout

The viewer should display assets grouped by family:

- **Terrain**: tiled preview showing repeat pattern.
- **Buildings**: per-faction grid showing each building PNG with its alpha-bounds overlay and footprint outline.
- **Civil units**: per-faction spritesheet preview with direction/frame grid.
- **Modular units**: per-faction direction grid showing hull + turret pairs.
- **Resources**: size comparison grid.
- **Decor**: simple grid.
- **FX**: animated preview where applicable.
- **UI icons**: icon set grid.

### 10.3 Features

- Asset key and filename displayed below each preview.
- Highlight for assets with warnings in the audit report.
- Toggle between source, staged, and generated views (if source/staged exist).
- Responsive layout; no server required (opens as a local file).

### 10.4 Implementation

The viewer should be a self-contained HTML file with embedded CSS and JavaScript. It reads `manifest.generated.json` and `audit-report.json` via `fetch()` and renders previews using standard `<img>` and `<canvas>` elements. No framework required.

## 11. Audit report responsibilities

### 11.1 Report format

`art/generated/audit-report.json` should contain:

```json
{
  "version": 1,
  "generatedAt": "2026-05-26T12:00:00Z",
  "summary": {
    "totalAssets": 106,
    "validAssets": 100,
    "warningAssets": 4,
    "errorAssets": 2
  },
  "warnings": [
    {
      "family": "buildings",
      "key": "building_cyan_separator",
      "code": "UNUSUAL_ASPECT_RATIO",
      "message": "Aspect ratio 1.33 exceeds typical building range (0.7-1.2)"
    }
  ],
  "errors": [
    {
      "family": "terrain",
      "key": "terrain_sand_grass",
      "code": "MISSING_FILE",
      "message": "Referenced file not found: art/staged/terrain/sand_grass.png"
    }
  ],
  "missingSource": ["art/source/modular/hunter_m0_source.psd"],
  "orphanFiles": ["art/staged/units/old_builder_test.png"]
}
```

### 11.2 Validation checks

| Check | Code | Severity |
|-------|------|----------|
| Referenced file not found | `MISSING_FILE` | Error |
| File exists but not referenced | `ORPHAN_FILE` | Warning |
| Key does not match family pattern | `INVALID_KEY_FORMAT` | Error |
| Filename does not match family pattern | `INVALID_FILENAME` | Warning |
| Spritesheet dimensions not divisible by frame count | `SHEET_DIMENSION_MISMATCH` | Error |
| Duplicate key across families | `DUPLICATE_KEY` | Error |
| Image has red/chroma-key background pixels | `SUSPECT_BACKGROUND` | Warning |
| Image fully transparent | `EMPTY_IMAGE` | Error |
| Source file missing for staged asset | `MISSING_SOURCE` | Warning |
| Aspect ratio outside family norms | `UNUSUAL_ASPECT_RATIO` | Warning |
| Icon size inconsistent within set | `ICON_SIZE_MISMATCH` | Warning |

### 11.3 Report output

The audit report is generated by the processor and can also be generated independently by `tools/validate_manifest.mjs`. The viewer reads the report and highlights issues.

## 12. Edge/crop/missing-source validation

### 12.1 Edge detection

For building and unit sprites, the processor should check:

- **Tight crop**: Is there excessive transparent padding? If more than 50% of the source image is transparent, warn about potential crop opportunity.
- **Near-edge content**: Are there non-transparent pixels within 2px of any edge? This may indicate the sprite was cropped too tightly and content may be clipped.
- **Stray pixels**: Are there isolated non-transparent pixels far from the main content? This may indicate artifacts.

### 12.2 Crop warnings

For spritesheets, the processor should verify:

- Frame dimensions divide evenly into sheet dimensions.
- Each frame has at least some non-transparent content (no fully blank frames).
- No frame content extends beyond the declared frame boundaries.

### 12.3 Missing source

For staged assets, the processor should check whether a corresponding source file exists in `art/source/`. If not, it issues a `MISSING_SOURCE` warning. This is informational only — not all staged assets need source sheets (e.g. simple PNGs may be authored directly).

## 13. Integration rules with PreloadScene/runtime

### 13.1 Current integration

PreloadScene manually calls four separate loaders. Each loader is responsible for its own key generation, path construction, and load type (image vs. spritesheet). There is no single entry point for "load all assets."

### 13.2 Current integration (ARCH-02F)

ARCH-02F has integrated the generated manifest into PreloadScene for hq + buildings families:

1. PreloadScene now calls `loadGeneratedBuildingAndHqAssets(this)` instead of the old manual `this.load.image(ASSET_KEYS.HQ_CYAN, ...)` + `loadBuildingAssets(this)`.
2. The generated loader reads from `src/assets/generatedAssetManifest.ts` (a committed TS file, not a runtime JSON fetch).
3. Duplicate key protection is built into the loader — it tracks loaded keys within each call.
4. The old `loadBuildingAssets()` is kept as deprecated legacy; its key/path helper exports remain available.
5. Other assets (terrain, harvester, minerals, modular units, civil units) still use their original loaders.

Full migration of all families to manifest-driven loading is deferred to later PRs.

### 13.3 Migration path

The migration from fragmented loaders to manifest-driven loading should be incremental:

1. **ARCH-02A**: Design only (this document). No runtime changes.
2. **ARCH-02B**: Manifest schema + validation script. No runtime changes.
3. **ARCH-02C**: Source/staged/generated folder structure + sample asset report. No runtime changes.
4. **ARCH-02D**: Processor/generator MVP for one family. Generates manifest JSON. No runtime changes.
5. **ARCH-02E**: Sample viewer. Reads generated manifest. No runtime changes.
6. **ARCH-02F**: Integrate validated generated assets into runtime manifest. This is the first phase that changes PreloadScene.

At each phase, the existing loaders continue to work. The manifest grows alongside them until ARCH-02F replaces them.

## 14. Relationship to existing building metadata generator

### 14.1 Compatibility

The building metadata generator (`tools/generate_building_meta.py`) produces `src/assets/generatedBuildingMeta.ts`. This file is imported by `src/assets/buildingPlacementMeta.ts` to populate the runtime registry. This system works correctly and must not be redesigned.

### 14.2 Integration

In the target architecture:
- The unified processor runs the building metadata generator as a sub-step.
- The building metadata output is incorporated into `manifest.generated.json` as additional metadata per building entry.
- `generatedBuildingMeta.ts` continues to exist and be imported by the runtime. The manifest does not replace it.
- The building metadata generator continues to be runnable standalone (`npm run generate:building-meta`).

### 14.3 No redesign

ARCH-02 does not redesign the building placement metadata system. It adds a layer around it for manifest management, validation, and preview. The building metadata generator, its output format, and its runtime consumption path are all preserved.

## 15. Risk-based ARCH-02 PR sequence

### 15.1 Proposed sequence

| Phase | Content | Risk | Runtime changes? |
|-------|---------|------|------------------|
| ARCH-02A | Audit/design docs (this document) | Low | No |
| ARCH-02B | Manifest schema JSON + `validate_manifest.mjs` script + unit tests | Low | No |
| ARCH-02C | Source/staged/generated folder structure + `.gitignore` + sample asset report | Low | No |
| ARCH-02D | Processor/generator MVP for one family (buildings) | Medium | No |
| ARCH-02E | Sample viewer (`task/art-sample/index.html`) | Low | No |
| ARCH-02F | Integrate validated generated assets into runtime manifest + update PreloadScene | Elevated | Yes |

### 15.2 Risk justification

- **ARCH-02A (low)**: Documentation only. No code, no assets, no runtime.
- **ARCH-02B (low)**: Schema + script. The script is dev-only, not part of the runtime bundle. Adds tests for validation logic.
- **ARCH-02C (low)**: Folders and gitignore only. No runtime impact. The sample asset report is informational.
- **ARCH-02D (medium)**: The processor generates files and a manifest JSON. It does not change runtime code. Risk is that the generated output is incorrect, but this is caught by validation and the sample viewer. Starting with one family (buildings) limits the blast radius.
- **ARCH-02E (low)**: The viewer is a standalone HTML file. It reads the manifest but does not modify it. No runtime impact.
- **ARCH-02F (elevated)**: This phase changes PreloadScene and potentially other runtime asset loading code. It replaces the fragmented loaders with manifest-driven loading. This is the highest-risk phase because it affects what assets the game loads at startup. It should be a separate PR with thorough manual QA.

### 15.3 Possible combination

ARCH-02B + ARCH-02C could be combined into one PR if the folder structure is trivial (just directories and a `.gitignore` entry). The manifest schema and validation script are the substantive part; the folders are scaffolding.

ARCH-02D + ARCH-02E could be combined if the processor MVP is simple enough and the viewer is lightweight. Combined risk would be medium (still no runtime changes).

ARCH-02F must remain separate because it changes runtime code.

### 15.4 Adjustment from proposed sequence

The original proposal in the task description was:
- ARCH-02A — audit/design docs
- ARCH-02B — manifest schema + validation script, no runtime changes
- ARCH-02C — source/staged/generated folder structure + sample asset report
- ARCH-02D — processor/generator MVP for one asset family, likely units or resources
- ARCH-02E — sample viewer for generated assets
- ARCH-02F — integrate validated generated assets into runtime manifest

This sequence is sound. The audit confirms it with one adjustment: ARCH-02D should target **buildings** rather than units or resources, because the building metadata generator already exists as a proven sub-processor for that family. Starting with buildings gives the processor a concrete existing tool to wrap, rather than building the first family from scratch.

## 17. Manual QA checklist

Before integrating generated assets into the runtime (ARCH-02F), the following manual checks must pass:

### 17.1 Visual checks

- [ ] All building PNGs render at correct scale and position in-game (compare before/after).
- [ ] All unit spritesheets animate in all 8 directions without visual artifacts.
- [ ] All modular unit direction PNGs display correct facing.
- [ ] All terrain tiles tile without visible seams or repetition artifacts.
- [ ] All resource sprites appear at correct size and alignment.
- [ ] No red-background or checkerboard artifacts in any asset.
- [ ] No unexpected transparent areas that should be opaque.

### 17.2 Functional checks

- [ ] Phaser loads all assets without `loaderror` events.
- [ ] No duplicate key warnings in console.
- [ ] No missing texture errors in console.
- [ ] Building placement metadata is consistent with generated building data.
- [ ] Spritesheet frame config matches actual sheet layout.

### 17.3 Process checks

- [ ] `validate_manifest.mjs` reports zero errors.
- [ ] `generate_building_meta.py` produces the same output as before (if building assets have not changed).
- [ ] `process_art_assets.mjs` completes without errors.
- [ ] Audit report has no `MISSING_FILE` or `DUPLICATE_KEY` errors.
- [ ] Sample viewer shows all expected assets with no broken images.

## 18. Open questions

### 18.1 Source sheet format

Should source sheets be committed to the repository, or only staged/generated assets? Source sheets may be large (PSD, high-res PNG). The recommended approach is to gitignore `art/source/` and commit only `art/staged/` and `art/generated/`, but this is a project decision.

### 18.2 Modular unit spritesheet migration

Should modular units (currently individual per-direction PNGs) be migrated to spritesheets? This would reduce the file count from 64 to 8 (2 sheets × 4 factions) and simplify loading. However, it requires changes to the modular unit renderer and is out of scope for ARCH-02. It could be considered for a later optimization pass.

### 18.3 Terrain tile atlas

Should terrain tiles be packed into an atlas/spritesheet for GPU efficiency? The current approach loads 3 individual images. A spritesheet would be more Phaser-idiomatic and would enable tile variation (ARCH-08). This is out of scope for ARCH-02 but should be considered when ARCH-08 is implemented.

### 18.4 FX/particle sprite format

FX sprites need a defined format. Individual PNGs vs. spritesheet vs. Phaser ParticleEmitter config? This should be decided when ARCH-13 (VFX) is implemented. For now, the pipeline supports individual `fx_{name}.png` files as a placeholder.

### 18.5 CI integration

Should `validate_manifest.mjs` run in CI? If so, it should be added to the GitHub Actions workflow. This is a low-risk enhancement that can be added at any phase after ARCH-02B.
