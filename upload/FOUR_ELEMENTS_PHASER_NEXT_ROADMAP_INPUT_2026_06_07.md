# Four Elements Phaser — набор желаемых направлений для большого roadmap-аудита

Дата: 2026-06-07  
Репозиторий: `ratoker-jpg/four-elements-phaser`  
Стек: HTML5 + TypeScript + Phaser 4 + Vite  
Статус документа: **не roadmap и не implementation plan**. Это исходный набор желаний/проблем/направлений от Дениса для большого системного аудита GLM.

## 0. Назначение документа

Этот документ нужен как вход в большой аудит.  
Сейчас не надо сразу писать код. Сначала нужно, чтобы GLM широко посмотрел текущий репозиторий, старые reference/donor-репозитории и предложил системный roadmap.

Формула работы:

```text
идея/набор хотелок -> большой аудит GLM -> предложения GLM -> GPT режет/структурирует -> roadmap -> scoped PR sequence -> реализация
```

Главное ограничение текущего будущего roadmap-а:

```text
НЕ ЛЕЗЕМ В РАЗРАБОТКУ БОТА / стратегического AI / enemy economy AI.
```

Можно анализировать всё остальное: режимы, UI, ассеты, производство юнитов, туман войны, территорию, движение, анимации, стрельбу, economy/progression, данные корпусов/пушек, UX по аналогии с RTS.

## 1. Текущая боль по main-ссылке и режимам

Проблема:

```text
https://ratoker-jpg.github.io/four-elements-phaser/
```

При открытии обычной ссылки/обычного режима не видно нормальных текущих ассетов корпусов и пушек. При этом в специальных ссылках вида `?devtools=1&arena=1` часть ассетов есть.

Ожидание:

В игре должны быть понятные режимы, доступные из интерфейса, без необходимости помнить магические query-параметры:

```text
1. Стандартный режим
2. Отладка / DevTools
3. Арена
```

Во все релевантные режимы нужно системно подключить текущие ассеты:

```text
- корпуса / hulls
- пушки / turrets
- fallback, если ассет не загружен
- правильная загрузочная политика, без preload всей матрицы
```

Нельзя оставлять ситуацию, где реальные ассеты видны только по технической ссылке, а основной вход показывает старые кубики/заглушки.

## 2. Локализация Arena/UI

Сейчас в Arena есть английские названия корпусов/пушек:

```text
Wasp, Hornet, Hunter, Viking, Smoky, Railgun, etc.
```

Нужно убрать английские названия из пользовательского интерфейса и перевести UX на русский.

Ожидание:

```text
- русские названия корпусов
- русские названия пушек
- русские подписи режимов
- русские названия команд/панелей/статусов
- технические asset IDs могут остаться английскими внутри кода
```

Важно: не смешивать runtime ID и user-facing label. Нужен слой display names/localization.

## 3. Против ручной пиксельной калибровки

Текущая проблема:

Мы уже несколько раз калибровали hull/turret scale/origin/offset вручную. Это плохо как основной production-подход.

Ожидание:

Нужны системные функции/профили/правила, которые отвечают за:

```text
- центрирование корпуса относительно ground anchor / selection ring
- размещение башни относительно mount/socket
- масштаб корпуса
- масштаб башни
- UI offsets для HP/labels
- fallback, если данных нет
```

При добавлении новых корпусов/пушек мы не должны снова страдать ручной настройкой каждого PNG без понятной модели.

Возможные направления для аудита:

```text
- asset metadata manifest
- visual profile per body/turret
- automatic bounds/anchor scanner offline, но не runtime PNG scan
- optional generated socket/muzzle metadata
- dev calibration overlay
- стандартизированный asset pipeline
```

Важно: runtime не должен читать PNG-пиксели. Если нужен анализ изображений, это должен быть offline tool / build-time validation.

## 4. Конфиги корпусов и пушек: роли, баланс, стоимость, уровни

Нужно полностью описать корпус и пушку как gameplay-сущности, а не просто картинку.

Для каждого корпуса нужно понять/описать:

```text
- роль
- HP
- броня / armor class
- скорость
- масса / весовая категория
- ускорение
- торможение
- поведение при старте/остановке
- доступность по tier HQ
- стоимость производства
- стоимость/условия апгрейда M0 -> M1 -> M2 -> M3
- визуальный asset id
- масштаб/профиль отображения
```

Для каждой пушки нужно понять/описать:

```text
- роль
- урон
- дальность
- скорострельность
- тип снаряда/луча/эффекта
- ресурс/перегрев/обойма/перезарядка, если есть
- доступность по tier HQ
- стоимость производства
- стоимость/условия апгрейда M0 -> M1 -> M2 -> M3
- визуальный asset id
- muzzle/socket metadata
```

Нужна балансная логика, чтобы корпуса и пушки не были хаотичным набором.

## 5. Tier-система T1/T2/T3

Нужно описать progression через улучшение базы/HQ.

Базовая идея:

```text
T1 — стартовая база.
Доступны начальные корпуса/пушки.
Пример: Wasp, Hunter, Smoky, Railgun.

T2 — база улучшена.
Открываются средние корпуса/пушки.

T3 — база полностью улучшена.
Открываются все корпуса/пушки.
```

Точные наборы должен предложить аудит на основе текущих configs/механик.

Ожидание:

```text
- HQ tier влияет на доступность корпусов
- HQ tier влияет на доступность пушек
- factory UI показывает locked/unlocked
- производить можно только доступные body+weapon combinations
- будущая возможность: на высоком tier производить сразу M1/M2/M3 за доплату
```

## 6. Unit Factory: производство конкретного танка

Нужно сделать производство не просто “создать юнита”, а сборку конкретной машины.

Ожидание UX:

```text
Игрок кликает на Unit Factory.
Открывается окно/панель производства.
Игрок выбирает:
- корпус
- пушку
- возможно модификацию, если доступно

UI показывает:
- стоимость корпуса
- стоимость пушки
- итоговую стоимость
- время производства
- требования по HQ tier
- locked/unlocked причину

Игрок подтверждает.
Factory ставит выбранный танк в очередь.
```

Нужно определить:

```text
- format production queue
- cost formula
- build time formula
- spawn point / rally point
- occupied-cell handling
- fallback if spawn blocked
```

## 8. Улучшение юнитов через опыт/урон/киллы

Нужно добавить механику апгрейда существующих танков.

Идея:

```text
Все танки создаются как M0.
Юнит получает прогресс не только за kill, но и за нанесённый урон.
Когда накоплен прогресс, появляется возможность upgrade.
Игрок выбирает, что улучшить:
- корпус
- пушку
```

UX:

```text
Выбран танк -> в центральной информационной панели есть Upgrade-кнопка/стрелка.
Можно улучшить body или weapon.
Показывается стоимость/требования/эффект.
```

В будущем:

```text
Если HQ T3 и ресурсов много, можно производить сразу M1/M2/M3 за доплату.
```

## 9. Движение без рывков

Проблема в текущем DevTools/Arena:

```text
танки едут с подёргиванием, будто каждую клетку делают мини-усилие
```

Ожидание:

```text
- плавное движение
- нормальное acceleration/deceleration
- без рывков на границах клеток
- корпус не должен “переступать” клетку рывком
```

Нужно проверить текущий movement/path-following и понять root cause.

## 10. Анимация направления корпуса и башни

Сейчас при смене direction PNG визуально похоже на slideshow.

Нужно:

```text
- плавная анимация разворота корпуса
- плавная анимация поворота башни
- не просто мгновенная смена dirXX PNG
- если 16 направлений недостаточно, аудит может предложить больше направлений или интерполяцию
```

Возможные направления:

```text
- angular smoothing
- turn rate per body/turret
- sprite direction hysteresis
- blended transition frames, если технически оправдано
- body turn animation separate from turret aim
```

Важно: не ломать точность target-lock и не добавлять top-down assumptions.

## 11. Движение как “масса”: старт, торможение, инерция, пыль

Нужно добавить визуальное ощущение веса.

Идея по классам:

```text
Лёгкие корпуса: Wasp, harvesters, builders
- быстрый старт
- заметный подъём передней части при резком старте
- сильная стартовая пыль
- меньше постоянной пыли
- заметный клевок при торможении

Средние корпуса:
- меньше подъём/клевок
- умеренная стартовая пыль
- стабильная пыль при движении

Тяжёлые корпуса: Titan, Mammoth
- медленнее разгон
- почти не поднимаются резко
- больше тяжёлой пыли под гусеницами
- инерционное торможение
```

Нужно распространять это не только на боевые юниты, но и на:

```text
- harvester
- builder
```

## 15. Миникарта и нижний RTS HUD по аналогии со StarCraft II

Используем StarCraft II как UX-референс, но не копируем ассеты/UI напрямую.

Желаемая структура нижнего UI:

```text
Лево: миникарта.
Центр: информационная панель выбранного объекта.
Право: панель быстрых команд/действий.
```

### 15.1 Миникарта

Показывает:

```text
- карту
- юнитов
- здания
- ресурсы
- fog/explored/visible
- territory control
- выбранный viewport
```

### 15.2 Центральная info panel

Если выбран танк:

```text
- название: Wasp + Railgun / русское имя
- HP
- kills
- rank/experience
- body mod M0/M1/M2/M3
- weapon mod M0/M1/M2/M3
- damage/speed/range/armor/basic stats
- активные улучшения
- кнопка upgrade, если доступно
```

Если выбран resource/crystal:

```text
- тип ресурса
- сколько осталось
- кто может добывать
```

Если выбрана factory/building:

```text
- HP
- текущая очередь производства
- доступные действия
- requirements/locked states
```

Если выбрано много юнитов:

```text
- список/иконки выбранных юнитов
- группировка по типам
- быстрый выбор подгруппы
```

### 15.3 Правая command panel

Зависит от выбранного объекта:

```text
Builder:
- построить здание
- repair / stop / hold / move etc.

HQ:
- upgrade T1/T2/T3
- produce builder/harvester, если это по дизайну верно
- global actions

Factory:
- produce tank
- choose body
- choose weapon
- queue controls

Combat unit:
- move
- stop
- attack
- hold position
- upgrade body
- upgrade weapon
```

Нужны hotkeys по RTS-логике:

```text
B для build menu у builder
командные hotkeys
tooltips
locked reasons
```

## 16. Режимы игры: standard / debug / arena

Нужно привести режимы к нормальной модели.

Ожидание:

```text
Standard:
- основной игровой режим
- normal player loop
- ассеты видны
- HUD виден
- fog/territory/economy/production доступны по roadmap

Debug:
- техническая отладка
- dev overlays
- entity inspectors
- asset previews
- может включаться из меню/параметра, но не должен быть единственным способом увидеть нормальные ассеты

Arena:
- sandbox для боя/визуала/баланса
- должна использовать те же asset systems, что и normal game, где это возможно
- не должна быть отдельным “другим движком”
```

## 19. Главный запрос к GLM

GLM должен не просто разложить мои желания по пунктам, а широко посмотреть проект и предложить своё:

```text
- что в текущей архитектуре мешает этим целям
- какие системы уже есть
- какие системы надо расширить
- где текущий код не готов
- что лучше сделать раньше
- что лучше отложить
- какие PR-шаги High/High+ нужны
- где нужны отдельные audits/design docs
- где можно переиспользовать Next/Sandbox как reference
- какие риски есть
```

Важно: не ограничивать GLM в предложениях, кроме запрета на bot development.
